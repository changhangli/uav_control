## 1. 对照范围 / 整机差异

对照范围：ArUco 靶标边长、相机分辨率与内参、识别 launch、降落 launch 参数。不对照 MID360 点云、FastLIO 建图或其它非视觉链路。

**一句话差异：** 官方是 MID360 + FastLIO + `sunray_uav_control`，靶标按 **0.42 m 外框**、小码 **0.052 m** / 大码 **0.212 m**，相机 **640×480**，丢码约 5 s 后直接降落；本机降落定位走 **mocap / teacher（`catkin_ws`）**，不用 FastLIO，靶标按实测约 **0.20 m 外框** 缩放成小码 **0.012 m** / 大码 **0.050 m**，头显相机 **1280×720**，降落逻辑额外加了 AGL、丢码是否落地、码数门槛和 home 回收。

| 项目 | 云纵官方 Wiki | 本机真飞 |
| --- | --- | --- |
| 定位 | MID360 + FastLIO | mocap / teacher（`catkin_ws`），本降落链路不用 FastLIO |
| 控制栈 | `sunray_uav_control` | 同系列控制节点，但 launch 参数已改 |

## 2. 靶标与识别码（重点）

官方降落垫外框 **0.42 × 0.42 m**。识别字典、码号两边一致；**改过的是物理边长 `markerLengths`**。

### 2.1 码表：ID 相同，边长不同

| 项 | 官方 Wiki json | 本机真飞 `aruco_detector_params.json` |
| --- | --- | --- |
| `dictionaryId` | 1 | 1（未改） |
| `markerIds` | 1–57 以及 91–94，共 61 个 | **同一组 61 个** |
| 小码边长 | 57 个 × **0.052 m** | 57 个 × **0.0120 m** |
| 大码边长 | 4 个 × **0.212 m**（id 91–94） | 4 个 × **0.0500 m**（id 91–94） |
| 其它 OpenCV ArUco 键 | Wiki 默认 | 与 Wiki 相同 |

本机另有官方 Wiki **没有** 的 `board_physical.yaml`（记录尺子实测 vs 官方 PDF 设计）：

| 键 | 本机值 | 含义 |
| --- | --- | --- |
| `board_side_m` | 0.20 | 当前板子外框边长（米） |
| `measured_small` | 0.012 | 尺子量到的小码边长 |
| `measured_large` | 0.050 | 尺子量到的大码边长 |
| `depth_scale` | 1.0 | 深度/尺度修正，1.0 表示不再额外放大缩小 |
| `design_*` | 官方 PDF：0.42 / 0.026 / 0.105 | 设计稿外框 / 小码 / 大码，**不是** Wiki json 里的 0.052 / 0.212 |

比例核对：`0.20/0.42 ≈ 0.476`，`0.026×0.476 ≈ 0.012`，`0.105×0.476 ≈ 0.050`。本机边长是按 **PDF 设计稿等比缩小到 0.20 m 板**，不是按 Wiki json 的 0.052 / 0.212 再缩。Wiki json 的 0.052 / 0.212 大约是 PDF 设计 0.026 / 0.105 的两倍，两边官方数字本身就不一致；真飞以尺子和当前 json 为准。

### 2.2 参数实际含义

**`dictionaryId`**  
OpenCV ArUco 字典编号。`1` 对应 `DICT_4X4_100`（4×4 比特、最多 100 个码）。检测器只在这个字典里找码；字典错了，画面上有码也认不出来，或会认成别的 ID。

**`markerIds` vs `markerLengths`**  
两列必须等长、按下标对齐：第 *i* 个 ID 的物理边长就是第 *i* 个 `markerLengths`（单位米，指黑色方块外沿）。  
- `markerIds`：允许出现在板上的码号。不在表里的码会被丢掉。  
- `markerLengths`：该码在真实世界里的边长。PnP 用「像素里占多大」和「你声称的米数」反推距离和位姿。

**小码 vs 大码**  
1–57 是铺满板面的小码，近距离、局部可见时仍能给出位姿。91–94 是四角大码，远一些、小码糊掉时仍能看见。检测器按 **每个 ID 自己的边长** 做 PnP，所以大码必须写大、小码必须写小；若 91–94 误写成 0.012，大码解出的深度会差约 4 倍。

**边长填错时，位姿尺度会怎样**  
PnP 深度大致与假定边长成正比：

`估计距离 ≈ 真实距离 × (填写边长 / 真实边长)`

例子：真实小码 0.012 m，若仍填官方 0.052 m，则 `0.052/0.012 ≈ 4.33`，相机会把板子「看」成远 4 倍，XY 偏差也会按同一比例放大。降落高度门槛、`error_xy` 全部会失效。反过来，若板子其实是官方 0.42 m、json 却写成 0.012，飞机会以为已经贴地。  
本机把 0.052→0.012、0.212→0.050，就是为了让解算尺度和 0.20 m 实物板一致。

## 3. 相机分辨率、设备、内参 yaml

### 3.1 驱动与分辨率

| 项 | 官方 `head_camera.yaml` / Wiki | 本机 `web_cam.yml` + `head_camera.yaml` |
| --- | --- | --- |
| 标定日期 | 2024-08-12 | 2026-08-05 |
| `camera_name` | `usb_cam` | `head_camera`（驱动） |
| 分辨率 | **640×480** | **1280×720** |
| 像素格式 | Wiki 未强调 | `mjpeg` |
| 帧率 | — | 30 |
| 设备 | 泛称 USB 相机 | `/dev/v4l/by-id/usb-DCXIN_DCXIN_Camera_01.00.000-video-index0` |

`image_width` / `image_height` 是 **当前正在推的画面尺寸**，必须和标定那张图的分辨率一致。内参（`fx fy cx cy`）是像素单位，随分辨率变。用 640×480 的内参去解 1280×720 的图，主点大约会偏在画面左上，焦距也会偏小，位姿会漂。

本机驱动开 1280×720，标定 yaml 也是 1280×720，两者对齐；官方是 640×480 对齐 640×480。

### 3.2 内参数字

| 参数 | 官方（约） | 本机（landmark 在用） | 实际含义 |
| --- | --- | --- | --- |
| `fx` | 580.7 | 740.50125 | X 方向焦距（像素）。越大，同样视角下物体在图上越大，或镜头更「长焦」。 |
| `fy` | 581.9 | 741.45705 | Y 方向焦距（像素）。与 `fx` 接近说明像素接近正方形。 |
| `cx` | 340.3 | 681.80051 | 主点 X：光轴打在图像上的列坐标。640 宽时约在 320 附近；1280 宽时约在 640 附近。本机 681.8 略偏右，属于标定结果，不是写错。 |
| `cy` | 231.5 | 367.26889 | 主点 Y。480 高时约 240；720 高时约 360。本机 367.3 接近中心。 |
| 畸变 | 官方 yaml 自带一组 | `[0.081779, -0.055899, 0.006339, 0.001372, 0]` | OpenCV 模型：`k1,k2,p1,p2,k3`。正 `k1` 多为桶形；检测前会先去畸变，否则码角点不准，近处位姿尤差。 |
| `P` 矩阵 | 官方对应 640×480 | 本机 `P` 的 fx 约 764.55 等 | 立体/去畸变后的投影矩阵；单目 ArUco 主要用 `K`（`fx fy cx cy`）+ 畸变。 |

`fx/fy` **不能**在两种分辨率之间按 1280/640=2 去倍乘来「换算」官方内参。本机 1280 的 `fx≈740`，官方 640 的 `fx≈581`，比值不是 2，说明镜头、安装、标定板都不是同一套，必须用 2026-08-05 这份，不能拿 Wiki 的 580 去跑 720p。

## 4. 识别 launch 差异

| 项 | 官方 `landmark_detection.launch` | 本机 |
| --- | --- | --- |
| `camera_name` | `/usb_cam` | **`/web_cam`** |
| 配置路径 | `sunray_tutorial` 下 | `landmark_detection` / `landmark_detection_ros` 包内（`~/vision_ws/src/sunray_vision_detection/landmark_detection/config/`） |
| `rotate` | 1 | 1（未改） |

`camera_name` 必须和相机节点发布的 namespace 一致。官方节点叫 `usb_cam`，本机 `web_cam.yml` 把相机叫 `head_camera`，检测 launch 订的是 `/web_cam`。订错话题则检测节点没有图，后面降落一直无码。

`rotate=1` 表示把图像旋转后再检测（安装朝向与「机头前方」不一致时用）。两边都是 1，旋转策略没有改。

## 5. 降落 launch / 算法参数

官方数字来自 Wiki 流程 + 官方包 `auto_land_by_pose.cpp` 默认值。本机数字来自 `auto_land_by_pose.launch`。`land_vel` 未改。

### 5.1 与官方 cpp 默认值直接可比的项

| 参数 | 官方默认 | 本机 launch | 实际含义 |
| --- | --- | --- | --- |
| `height` | 1.5 | **1.8** | 进入降落流程后先到的悬停/接近高度（米，相对所用高度基准）。本机抬高 0.3 m，给视觉对齐多留一点余量。 |
| `error_xy` | 0.05 | **0.10** | 水平对准门限（米）。位置误差小于该值才允许往下收。本机放宽到 10 cm：码尺度变小、720p 噪声不同，5 cm 过严会在空中来回蹭。 |
| `error_z` | 0.25（cpp） | **0.20**（launch） | 高度方向「已经够低、可以进入下一阶段」的门限（米）。与 `land_agl`、`drop_height` 不是同一个开关，见 5.4。 |
| `land_vel` | 0.3 | 0.3 | 降落段垂直速度上限（m/s）。 |
| `last_land_time` | 1.5 | **0.5** | 最后一段「确认要落地」的保持时间（秒）。官方 1.5 s；本机 0.5 s，切油门/切 LAND 更快。 |
| `drop_height` | 0.15 | **0.05** | 认为已经贴地、可以结束视觉引导的剩余高度（米）。官方 15 cm 再丢；本机 5 cm，因为板子矮、且另有 `land_agl`。 |
| `auto_takeoff` | false | （沿用 false 一类） | 是否由该节点自动起飞。降落脚本通常为 false。 |

### 5.2 本机新增（Wiki / 官方 cpp 没有）

| 参数 | 本机值 | 实际含义 |
| --- | --- | --- |
| `land_agl` | 0.18 | 距地（AGL）低于 18 cm 后进入贴地逻辑。用测距/高度计，不是 ArUco 解出来的 z。 |
| `final_land_z` | 0.15 | 视觉坐标系里「最终落地」参考高度（米）。 |
| `land_on_lost_tag` | false | 丢码后 **不** 自动落地。官方是丢码等 5 s 再降落。 |
| `lost_tag_timeout` | 8.0 | 连续看不到码超过 8 s 才触发丢码反应。 |
| `lost_tag_react` | 0.6 | 丢码后的反应强度/过渡（秒级）。不是再等 5 s 下砸。 |
| `approach_floor_z` | 0.50 | 接近段最低高度：先收到约 0.5 m，再精细对准。 |
| `approach_xy` | 0.15 | 接近段水平门限（米），比最终 `error_xy` 松。 |
| `low_land_z` | 0.20 | 低空段高度门槛。 |
| `align_gain` | 1.0 | 水平对准控制增益，1.0 为不额外放大。 |
| `slow_drop` | 0.05 | 末端慢降速度（m/s），比 `land_vel` 0.3 更慢。 |
| `min_start_z` | 0.50 | 低于约 0.5 m 不重新开「从高处开始对准」的流程。 |
| home | `0, 0, 1` | 视觉丢失或需要回收时的家点（x, y, z）。 |
| home `xy_tol` | 0.20 | 到家点水平容差 20 cm。 |
| home `z_tol` | 0.12 | 到家点高度容差 12 cm。 |
| home hover | 2.5 s | 到家后悬停再进入后续。 |

### 5.3 码数门槛（官方没有）

ArUco 板同时能看到的码越多，PnP 越稳。本机用「至少看见几枚码」决定能否进入该阶段：

| 参数 | 本机值 | 含义 |
| --- | --- | --- |
| `align_min_markers` | 1 | 水平对准：至少 1 枚码。远距离往往只能看见大码。 |
| `descend_min_markers` | 2 | 开始往下收：至少 2 枚，降低单码跳变导致的斜着往下冲。 |
| `fine_min_markers` | 4 | 精细段：至少 4 枚。近了小码会大量出现，用多码平均。 |
| `align_exit_markers` | 0 | 退出对准的码数下限；0 表示不靠「码变少」退出。 |

官方逻辑不按码数分阶段，主要靠 `error_xy` / `error_z` / 丢码计时。

### 5.4 `land_agl` vs `error_z` vs `drop_height`

三个都带「高度」，管的不是同一件事：

1. **`error_z`（本机 0.20）**  
   视觉解算的相对高度误差门限：z 方向已经够接近目标高度，才认为「高度对准完成」，可以进入更低的阶段。它看的是 **码解出来的位姿**。

2. **`drop_height`（本机 0.05，官方 0.15）**  
   视觉引导还剩多少高度就结束、交给最后落地。官方 15 cm 就收工；本机收到 5 cm，因为板矮、怕 15 cm 就切 LAND 会砸偏。

3. **`land_agl`（本机 0.18，官方无）**  
   **离地高度** 门限（雷达/气压/融合 AGL），用来判断「已经贴近地面」。ArUco 在极近处可能出画面或尺度噪声大，AGL 是独立保险。0.18 m 与 `final_land_z` 0.15、`drop_height` 0.05 一起用：视觉收到很低，同时 AGL 也确认贴地。

不要把 `error_z=0.20` 理解成「离地 20 cm 就降落」：那是对准误差带；真正贴地看 `drop_height` 和 `land_agl`。

检测节点在 **vision_ws**，不在 `land_ws`。下面三份边长不要混用。

## 7. 真飞怎么开（机载脚本，不是手敲 roslaunch）

已在 `uav@192.168.50.151` 的 `~/uav_worklog/scripts/` 核对。真飞终端用脚本，不要手敲 `roslaunch`。

**真飞主路径：home_land**

```bash
bash ~/uav_worklog/scripts/start_home_land.sh
```

停（会停掉 home_land 的降落节点 `/auto_land_1`，以及它拉起的视觉栈）：

```bash
bash ~/uav_worklog/scripts/stop_land_stack.sh
```

`start_home_land.sh` 会后台起 `start_vision_verify.sh --daemon`（相机 + 地标识别 + 门控），再 `roslaunch sunray_tutorial auto_home_land.launch`（`home_land_mode:=true`，内部 include `auto_land_by_pose.launch`，节点名 `/auto_land_1`）。`stop_land_stack.sh` 用 `rosnode kill /auto_land_1` 停降落，再调用 `stop_vision_verify.sh`。

地面站仍先解锁 → 起飞 → 选视觉航线。手持不解锁加 `--bench`。

**标定**（有桌面、`DISPLAY`；相机须已出图）：

```bash
bash ~/uav_worklog/scripts/run_camera_calibrate.sh
```

**另外两套（不是真飞主路径）**

| 脚本 | 何时用 |
| --- | --- |
| `start_land_stack.sh` | 旧路径：视觉 + bag 后台，等老师悬停后按回车再起 `auto_land_by_pose.launch`（无杀 demo / 回原点）。停同样 `stop_land_stack.sh`。 |
| `start_vision_verify.sh` | 只起视觉、不起降落。看图对板用。只停视觉：`stop_vision_verify.sh`。 |
