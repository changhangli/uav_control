## 一、今天完成了什么

### 1. 摸清视觉包结构与分工

`~/vision_ws/src/sunray_vision_detection` 内主要包：

| 包 | 作用 | 本项目是否主用 |
|---|---|---|
| `web_cam` | USB 相机驱动，发 `/web_cam/image_raw` | 是 |
| `landmark_detection` | 多 ArUco 融合为板中心，精准降落 | **是** |
| `qrcode_detection` | 每个二维码单独输出，偏跟随 | 否 |
| `ellipse_detection` | 椭圆/圆形靶标 | 暂不用 |
| `detection_msg` / `detection_libs` | 消息与底层检测库 | 依赖 |

结论：精准降落应跑 `landmark_detection`，不是单个二维码检测。

降落板构成：
- 小码 ID 1–57，大码 ID 91–94（边长约为小码 4 倍）
- 共约 61 个码，合起来是**一个靶标**，不是 61 个指令
- 每个 ID 在 `id_value.h` 的 `pose_table` 里有固定板面位置
- 多码各自反推板中心 → 简化 RANSAC 融合 → 输出一条 `px,py,pz`

### 2. 跑通识别链路

启动链：
`roscore` → `web_cam` → `landmark_detection` →（可选）`rqt_image_view` / 记录脚本

输出话题（注意名字）：
- 原始融合结果：`/uav1/sunray_detect/qrcode_detection_ros`
- 可视化：`.../image_rect`
- 门控后（给飞控用）：`/uav1/sunray_detect/landmark_pose_gated`

融合结果字段真实含义（容易误解）：
- `cx/cy/h/los_*`：融合输出里常为 0，**不是坏了**
- `category_id`：本帧认出的码数（不是某个码 ID）
- `w`：用到的大码数
- `tracked_id`：参与融合的码数
- `score`：RANSAC 误差，**越小越好**
- `px,py,pz`：板中心相对相机，单位**米**

### 3. 弄清三个核心问题

**（1）原点在哪**  
在相机光心，不在机体中心。全链路原先无相机→机体外参。  
`x_bias/y_bias` 不是机体偏移，只微调板中心在靶标平面内的定义。

**（2）markerLengths 与打印尺寸**  
```
json 边长（米） = 纸上黑色正方形边长（米）   # 1:1
大码 ≈ 4 × 小码
整板边长 ≈ 15 × 小码
距离 ∝ markerLengths，也 ∝ 焦距 fx
```

屏幕联调：整板约 15.6 cm（设计图标注 0.42 m）  
缩放比 ≈ 0.156/0.42 ≈ 0.371  
→ 小码 ≈ 0.0097 m，大码 ≈ 0.0390 m

**（3）画面旋转 rotate**  
当前 launch 为 `rotate=0`。手持验证：相机左移→画面右移，相机上移→目标下移，符合未旋转。  
等下视安装后再定是否改为 `1`（180°）。

### 4. 坐标轴向

已在门控输出做：`py = -py`。

## 二、踩过的坑（重要）

### 坑 1：话题名叫 `qrcode_detection_ros`，不是 bug

`landmark_detection` 发布话题硬编码为 `qrcode_detection_ros`。  
官方文档验证命令就是 echo 这个名字，下游 `auto_land` 也订它。  
**不要擅自改名。**

### 坑 2：1280×720 只改了宽高，没改正内参

`head_camera.yaml` 曾被改成 `1280×720`，但 `camera_matrix` 仍是约 640×480 那套（`cx≈340, cy≈231`）。  
正确 1280×720 主点应接近 `(640, 360)`。  
症状：`fov_x≈95.5°` 明显偏大；绝对距离不可信。  
**必须用本相机在 1280×720 下重新标定。**

### 坑 3：单个孤立 ArUco 不能拿来测 landmark

`landmark_detection` 假定看到的码都是官方板上的码。  
只放一个 ID=1 时，会按 `pose_table` 外推“整板中心”，`px/py` 会离谱。  
测单码应用 `qrcode_detection`；测板中心必须用完整板。

### 坑 4：改 json 导致节点崩溃（CRLF）

报错：`Parameter markerIds.length != markerLengths.length!`  
根因：原 `aruco_detector_params.json` 是 **CRLF**（`\r\n`）。  
用 Python `write_text` 会变成 LF，他们的 gason 解析器读数组长度错乱。  
解决：改配置必须保持 CRLF；`apply_board_size.py` 已按字节替换并保 CRLF。

### 坑 5：话题名打错 `uac1`

正确是 `/uav1/...`，不是 `/uac1/...`。

### 坑 6：一键启动脚本早期有两个 bug

1. Ctrl+C 会连带杀掉 roscore/相机（同进程组）→ 已改为 nohup/disown  
2. 用 `timeout rostopic hz` 做就绪判断，超时退出码 124 被当成失败，卡在“等待节点就绪”→ 已改为 `rostopic echo -n 1` 判断

### 坑 7：屏幕验证废数据比例高

原因叠加：屏幕反光/摩尔纹、手持晃动、内参未标定。  
不等于算法完全不可用；固定段可以很稳（曾有连续约 26 帧 `pz≈0.25m`）。  
真飞必须门控；实体印刷板会好很多。

### 坑 8：`rqt` 画面“卡住”

后台话题仍 30Hz 且帧内容在变。  
多半是 `rqt_image_view` 显示问题：关掉重开、确认话题、取消 Pause。

### 坑 9：`x_bias/y_bias` 误以为是机体偏移

不是。机体偏移应加在最终 `px/py/pz` 上（现已在门控配置里预留 `body_offset_*`）。

### 坑 10：ellipse_detection 的 launch 是抄的二维码

文件名/包名仍指向 qrcode，暂不影响本项目主线。
